## 一、产品定位与核心差异化

### 1.1 IRAgent 和其他平台的根本区别

```
其他平台的逻辑：
  题目数据库（人工录入）→ 按标签匹配 → 返回固定题目 → 通用解析

IRAgent 的逻辑：
  学生笔记（AI 阅读理解）→ 学生错题（AI 诊断薄弱点）
  → AI 实时生成个性化题目 → 解析引用笔记原文
```

| 对比维度 | 作业帮/猿题库 | ChatGPT/通义 | **IRAgent（当前）** | **IRAgent（Phase 2）** |
|---------|-------------|-------------|-------------------|---------------------|
| 题目来源 | 人工录入的固定题库 | 互联网训练数据 | **种子数据 + 用户上传，SQL 查询** | **AI 根据笔记实时生成** |
| 题目针对性 | 按考点标签匹配 | 泛泛而谈 | **薄弱考点优先 + 随机补充** | **分析错题+笔记 → 出专攻题** |
| 解析风格 | 通用解析模板 | 通用解析 | **通用解析（种子数据自带）** | **解析引用笔记原文** |
| 组卷逻辑 | 标签规则拼凑 | 无法组卷 | **规则引擎 + 难度自适应** | **AI 理解掌握度 → 从易到难设计** |
| 学习闭环 | 做题 → 看答案 | 提问 → 得到答案 | **笔记→练习→诊断→复习** | **AI 自适应闭环** |

> **架构备注**：当前 Milvus 按用户建 Collection（`kb_notes_{userId}`），适合千级用户规模。生产环境万级以上需改为单 Collection + `user_id` 分区键或按租户分片，避免 etcd 元数据瓶颈。本阶段为演示项目，per-user Collection 保留。

### 1.2 AI 在 IRAgent 中的角色

```
AI 不是"一个功能"，AI 是"引擎"。

┌─────────────────────────────────────────────────────────────┐
│                       AI 引擎层                              │
│                                                             │
│  ┌───────────┐  ┌───────────┐  ┌───────────┐  ┌──────────┐ │
│  │ 笔记理解   │  │ 错题诊断   │  │ 题目生成   │  │ 解析锚定  │ │
│  │ 提取知识点 │  │ 多路并行   │  │ 实时出题   │  │ 引用原文   │ │
│  │ 构建图谱   │  │ 定位根因   │  │ 变式改编   │  │ 精准讲解   │ │
│  └───────────┘  └───────────┘  └───────────┘  └──────────┘ │

└─────────────────────────────────────────────────────────────┘
```

## 二、核心数据闭环

### 2.1 学习飞轮

**新用户冷启动路径**：

```
新用户首次登录
  │
  ├─ 路径 A：有笔记 → 上传笔记 → AI 理解 → 构建知识图谱
  │    若笔记总量 < 1000 字（碎片化）→ 自动触发路径 B 简化诊断
  │    前端提示："笔记很棒！但内容较少，建议花3分钟完成微诊断"
  │
  └─ 路径 B：没笔记 → 新手诊断测验（自适应出题）
                        │
                        ▼
                 自适应诊断测验：
                   · 第 1 题：中等难度通用题
                   · 答对 → 提升同考点难度
                   · 答错 → 降低难度
                   · 每考点测 3-5 题，跨越两个难度层级即停止
                   · 通常 10-15 题可完成初始画像
                   · （远期可升级为完整 IRT-CAT，当前用简化规则版）
                        │
                        ▼
                 生成初始掌握度画像（每考点 0~1 + 置信度）
                        │
                        ▼
                 AI 据此出每日一练（基础巩固题为主）
                 前端标注"完成首次诊断，已为你生成专属练习"
                        │
                        ▼
                 用户边用边上传笔记 → 逐渐过渡到个性化模式
```

> **设计要点**：不能假设所有用户一上来就有笔记。没笔记+没错题时，掌握度画像为空，AI 出题引擎无法工作。需要在 Onboarding 环节或首次进入刷题 Tab 时触发诊断测验。

**完整学习飞轮**（已有笔记+错题的用户）：

```

                        │   上传笔记     │

                        │ 提取知识点+公式 │
                        └──────┬───────┘
                               │

              │  · 知识点图谱（考点→笔记→题目）   │

              │      (难题惩罚更重，易题惩罚更轻)     │
              │    - 难题(4-5)权重×1.5，易题(1-2)×0.7 │
```

### 2.2 数据流全景

```
学生笔记 ──→ AI 阅读理解 ──→ 知识图谱
                              │
学生错题 ──→ DAG 诊断 ──→ 薄弱点画像
                              │
                              ├──→ 答疑：AI 检索笔记 + 流式回答 + 引用原文
                              │
                              ├──→ 每日一练：AI 接收(薄弱考点+笔记原文+错题类型)
                              │         → 生成 5 道专攻题
                              │         → 存入 question 表
                              │         → 语义缓存（同考点不重复调 LLM）
                              │
                              ├──→ 智能组卷：AI 接收(掌握度雷达+笔记范围+目标考试)
                              │         → 设计从易到难的试卷结构
                              │         → 逐题生成 → 整套存入 question 表
                              │
                              └──→ 真题模拟：AI 接收(考试类型+年份+薄弱点)
                                        → 生成符合考纲风格的模拟题
                                        → 存入 question 表（source=ai-generated）
                                        → 后续请求 → 缓存直接返回
```

## 三、Tab 1：知识库 — AI 学习学生的笔记

### 3.1 业务流程

```
学生上传笔记（PDF/Markdown/TXT/图片）
        │
        ▼
┌─────────────────────────────────────────┐
│  Step 1: 文本提取                        │
│  · PDF → 文字提取                       │
│  · 图片 → OCR 识别                      │

├─────────────────────────────────────────┤
│  Step 2: AI 结构化理解                   │
│  · NoteChunkingService：按章节标题切分   │
│  · 每段 chunk 关联一个知识点             │
│  · 提取：公式、例题、定义、易错提示       │
├─────────────────────────────────────────┤
│  Step 3: 向量化入库                      │
│  · Embedding（2048维）→ Milvus 用户专属  │
│  · Collection: kb_notes_{userId}        │
│  · PostgreSQL: note + note_chunk 双写   │
├─────────────────────────────────────────┤
│  Step 4: 知识图谱构建                    │
│  · 考点 ↔ 笔记片段 ↔ 关联题目            │
│  · Android 端 SVG 可视化                │
└─────────────────────────────────────────┘
```

### 3.2 关键设计：AI 理解笔记，不只是存储

```
笔记原文：
  "求 f(x) 在 [a,b] 上最值：1.求导找驻点 2.计算 f(驻点),f(a),f(b)
   3.排序比较。⚠️ 易错点：忘记计算端点值！"

AI 理解后提取：
  {
    考点: "闭区间最值",
    公式: ["f'(x)=0 求驻点"],
    步骤: ["求导", "算驻点值", "算端点值", "排序比较"],
    易错: ["漏算端点值", "驻点=最值点混淆"],
    变式思路: ["区间改为开区间", "增加不可导点", "混合参数"]
  }
```

**后续出题时，AI 用这些结构化信息生成变式题——改区间、加参数、混合考点。**

> **实施提醒**：若 IRT 自适应算法实施周期过长，可先用简化版——预设 3-4 个难度层级，答对升层、答错降层，每考点测 3-5 题，难度跨越两级即停止。

## 四、Tab 2：答疑 — AI 检索笔记 + 流式回答

### 4.1 业务流程

```
用户输入问题
        │
        ▼
┌─────────────────────────────────────────┐
│  Step 1: 意图路由（IntentRouter）         │
│  · 识别关键词 → 5 种模式：                │
│    HINT_NEEDED      → 苏格拉底引导       │
│    FULL_EXPLANATION → 完整解答+笔记引用   │
│    NOTE_SEARCH      → 检索笔记原文        │
│    PRACTICE_READY   → 推荐同类变式题      │
│    GENERAL          → 兜底，通用问答      │
├─────────────────────────────────────────┤
│  Step 2: 三路并行检索                    │
│  · 个人笔记 Milvus：语义相似度检索        │
│  · 真题库 Milvus：HNSW 向量检索           │
│  · PostgreSQL：GIN 全文检索              │
│  → RRF 三路融合重排 → Top-10 上下文       │
├─────────────────────────────────────────┤
│  Step 3: System Prompt 组装              │
│  · 角色定义 + 回答风格                    │
│  · 检索到的笔记片段（标注来源）            │
│  · 检索到的真题上下文                     │
│  · 对话历史（最近 10 条）                 │
├─────────────────────────────────────────┤
│  Step 4: LLM 流式调用（SSE 返回）         │
│  · chunk：逐字文本                        │
│  · note_refs：笔记引用卡片                │
│  · plot/plot3d：函数图像数据              │
│  · done：流结束                          │
├─────────────────────────────────────────┤
│  Step 5: 持久化 + 窗口降级                │
│  · conversation 表（自动创建/更新）        │
│  · message 表（用户 Q + AI A）            │
│  · Redis 对话历史缓存（最近 10 条）        │
│  · Token 超限降级：若笔记片段+历史超过     │
│    模型窗口 → RRF 得分截断（仅保留 >0.85） │
│    → 历史对话摘要压缩（Summary Buffer）    │
└─────────────────────────────────────────┘
```

### 4.2 SSE 事件流规范

```
请求：POST /api/v3/chat/stream
      { question: "...", conversationId?: "xxx" }

事件序列（按时间顺序）：

  data: {"type":"chunk","data":{"content":"好的，让我"}}
  data: {"type":"chunk","data":{"content":"结合你的笔记来分析..."}}
  ...
  data: {"type":"plot","data":{"expr":"x^3-6x^2+9x","xmin":0,"xmax":4}}
  ...
  data: {"type":"chunk","data":{"content":"答案是对的，但..."}}
  ...
  data: {"type":"note_refs","data":{"noteRefs":[
    {"noteFragment":"求f(x)在[a,b]上最值...⚠️易错：忘记计算端点值！","similarity":0.92}
  ]}}
  data: {"type":"done","data":{}}

SSE 断线重连：连接建立时后端返回 stream_id。网络切换断开后，
前端带 stream_id + 已接收的 chunk_index 重连，后端从 Redis 续流。
前端对 plot/plot3d 事件异步渲染，避免图像渲染阻塞文本流。
```

## 五、Tab 3：刷题 — 当前基于题库 SQL 查询，AI 出题为 Phase 2 规划

### 5.1 当前实现与规划

```
当前实现（Phase 0-1，已上线）：
  question 表（种子数据 + 用户上传）→ 按策略 SQL 查询 → 返回固定题目

Phase 2 规划（AI 出题引擎）：
  AI 接收（笔记 + 错题 + 掌握度）→ AI 实时生成个性化题目 → 解析锚定笔记
                                    ↓
                              存入 question 表
                              （首次 LLM 生成，之后缓存命中）
```

> **面试话术**："刷题模块采用 SQL 题库 + AI 生成双引擎架构。常规题目走 SQL 查询（种子数据覆盖考研/专升本/高考核心考点），题库空竭时 `AIQuestionGenerator` 自动接管——根据考点、难度和题型生成新题，解析标注验证级别。生成结果走三级缓存：Redis 精确缓存（<1ms）→ Milvus 语义改写（复用骨架）→ LLM 完整生成（<0.85 全新出题）。同一考点不重复调 LLM，Token 成本可控。"

### 5.2 每日一练 — 当前：60% 薄弱考点 + 40% 随机（SQL 查询）

```
请求：GET /api/v3/daily-practice?subject=数学&count=5
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│  当前实现（DailyPracticeService）                            │
│                                                             │
│  Step 1: 查薄弱考点关联题目（60%）                            │
│    SELECT q.* FROM question q                               │
│    INNER JOIN error_book e ON q.knowledge_point = e.knowledge_point
│    WHERE e.user_id = ? AND e.mastered = false               │
│    AND q.id NOT IN (今日已做过)                              │
│    ORDER BY RANDOM() LIMIT ?                               │
│    若返回空（新用户无错题记录）→ 降级：                          │
│    SELECT 掌握度画像 < 50% 的考点 → 取对应 question 表题目     │
│    若仍为空（无画像数据）→ 直接走 Step 2 随机补充              │
│                                                             │
│  Step 2: 随机补充（40%）                                     │
│    SELECT * FROM question                                   │
│    WHERE subject = ? AND status = 'published'               │
│    AND id NOT IN (今日已做过)                                │
│    ORDER BY RANDOM() LIMIT ?                               │
│                                                             │
│  Step 3: 不足时补齐 → 继续随机取                              │
│                                                             │
│  【Phase 2 规划】替换为 AI 生成：                             │
│    接收(薄弱考点 + 笔记原文 + 错题类型) → LLM 生成 5 道专攻题   │
│    基础巩固 ×2 + 混合考点 ×2 + 陷阱变式 ×1                    │
└─────────────────────────────────────────────────────────────┘
        │
        ▼
  返回 5 道题 + sessionId → 学生逐题作答 → 提交批改
```

### 5.3 智能组卷 — 当前：规则引擎拼凑（SQL 查询）

```
请求：POST /api/v3/paper/smart
      { subject, examType, title, questionCount, difficulty, knowledgePoints?, excludeDone }
        │
        ▼
┌─────────────────────────────────────────────────────────────┐
│  当前实现（SmartPaperService + PaperStrategyService）        │
│                                                             │
│  Step 1: 确定考点                                            │
│    传了 kps → 按给定考点分配                                 │
│    没传 → 从 error_book 取薄弱考点 Top 4                     │
│                                                             │
│  Step 2: 确定难度分布（自适应，按考点分别计算）                │
│    取该考点的掌握度画像值：                                     │
│      该考点掌握度 <40% → 80%易+20%中+0%难（薄弱时不推难题）   │
│      该考点掌握度 40-70% → 20%易+50%中+30%难                 │
│      该考点掌握度 >70% → 10%易+40%中+50%难                   │
│    无画像数据的新考点 → 默认掌握度 50%（中等偏下）              │
│                                                             │
│  Step 3: 题型比例 → 选择40% + 填空30% + 解答30%              │
│                                                             │
│  Step 4: 从 question 表查题（SQL）                           │
│    考点 × 难度 × 题型 → SELECT ... ORDER BY RANDOM() LIMIT N│
│    excludeDone → 排除 user_answer_record 中已做对的题         │
│                                                             │
│  Step 5: 组装试卷                                           │
│    每题分配得分 → 选择题在前 / 填空居中 / 解答在后             │
│                                                             │
│  【Phase 2 规划】替换为 AI 出卷：                             │
│    AI 设计试卷结构（易→中→难）+ 逐题 AI 生成                  │
└─────────────────────────────────────────────────────────────┘
```

### 5.4 真题模拟 — 当前：question 表筛选（SQL 查询）

## 九、AI 出题缓存策略（Phase 2 规划）

> ⚠️ 当前出题为 SQL 查库模式，以下缓存策略为 AI 出题改造后的目标架构。

```
用户请求出题（每日一练/组卷/真题模拟）
        │
        ▼
┌─────────────────────────────────────────┐
│  Step 1: 精确缓存（Redis）               │
│  每日一练: gen:{userId}:{kp}:pool:{date}  │
│  智能组卷/真题: gen:{userId}:{kp}:pool:{weekId}│
│  → 命中：从缓存池随机抽取 n 道（避免同套复用）│
│  → 前端随机打乱顺序                      │
│  → 未命中或池中题量不足：进入 Step 2      │
├─────────────────────────────────────────┤
│  Step 2: 语义缓存改写（Milvus）           │
│  请求向量化 → 查 question 表已有题目     │
│  → 相似度 > 0.90：复用原题骨架            │
│  → LLM 仅改写数值/情境（远比完整生成便宜） │
│  → 未命中：进入 Step 3                  │
├─────────────────────────────────────────┤
│  Step 3: AI 完整生成                      │
│  LLM 生成新题 → 答案自动验证（Section 13）│
│  → 验证通过 → 存入 question 表            │
│  → 验证失败 → 丢弃 + 日志 + 重试          │
│  → 向量化存入 Milvus（下次命中 Step 2）   │
│  → 写入缓存池（下次命中 Step 1）          │
└─────────────────────────────────────────┘
```

**Token 成本预估**（目标值）：
- 首次出题：调用 LLM（~500-1000 Token/题）
- 第二次同考点出题：Redis 缓存命中（0 Token）
- 语义相似考点出题：Step 2 命中已有题目（0 Token）
- **缓存命中率目标 > 80%，日均新增 LLM 调用 < 10 次/用户**

## 十二、工程落地考量与风险应对

### 12.1 AI 生成延迟：首次组卷可能超过 20 秒

**风险**：智能组卷若 AI 逐题串行生成 20+ 道题，延迟不可接受。

**应对**：
- **预生成策略**：用户上次答题后，后台异步预生成下一次的每日一练题目。预生成结果带掌握度画像 hash 版本号——若画像在预生成后发生变化（用户又做错了新题），自动作废并重新生成
- **渐进加载**：组卷时先渲染前 5 道，后续题目边做边生成
- **小模型评估**：评估 DeepSeek-7B/13B 微调模型专门负责数学题生成，降低成本与延迟

### 12.2 笔记隐私：原文直接喂给云端 LLM

**风险**：笔记内容可能包含学生姓名、学校等隐私信息，直接传给云端大模型存在合规风险。

**应对**：
- 发送 LLM 前对笔记片段做**实体识别脱敏**（替换人名/地名/学校名）
- 答疑检索时优先传递知识点摘要，非必要不传全文
- 长期评估私有化部署模型处理含笔记原文的请求

### 12.3 语义缓存多级阈值策略

**风险**：单一阈值（0.96）命中率过低，同一考点的小变式题穿透到 LLM 生成，缓存收益有限。多级阈值策略（Section 9）：[0.90, 1.0] 改写数值，[0.85, 0.90) 改编情境，<0.85 完全生成。

**应对**（多级缓存策略）：
- **精确缓存**（考点 + 难度 + 题型 完全匹配）→ 命中直接复用
- **语义缓存**（相似度 > 0.90）→ 复用原题骨架，LLM 仅改写数值/情境（远比完整生成便宜）
- **完全生成**（相似度 < 0.85）→ 完整 LLM 生成新题
- 线上持续监控命中率，动态调整各级阈值

### 12.4 数学公式 OCR 与 Embedding 精度

**风险**：公式在 PDF/图片中需要精准识别为 LaTeX，否则知识提取和后续题目生成失真。公式的语义 embedding 容易丢失。

**应对**：
- 引入专用数学 OCR（如 Mathpix API）或支持公式解析的模型
- 向量化前将公式统一转为 LaTeX 文本再 Embedding
- 检索时对公式段提高权重，减少语义漂移

### 12.5 真题版权保护

**AI 生成约束规则**：
- 禁止逐字复制真题原文，只模拟题型、知识点分布和难度结构
- AI 生成的题目 `source` 字段标记为 `ai-generated`，前端标注"AI 生成，仅供参考"
- 知识图谱引入标准考纲节点作为骨架，笔记内容挂载其上，保证考点全覆盖

### 12.6 学习计划模块（Phase 2）

**当前缺口**：产品是"工具集"（笔记、答疑、刷题、错题本、仪表盘），缺少一条明确的学习路径。

**规划**：
- 学生选择目标（如"两个月攻克高数上"）→ AI 拆分阶段性任务
- 自动串联每日一练 + 智能组卷 → 形成学习计划
- 仪表盘增加"计划进度"卡片
- 未覆盖的考纲考点 → 主动提醒"你还没有 XX 考点的笔记，需要学习建议吗？"

### 12.7 缓存池题目退化监控

**风险**：缓存策略生效后，某考点题目池长期不被 LLM 刷新，题目变体不足，学生反复遇到同类题。

**应对**：
- 监控指标：每考点缓存池题目数量、最后生成时间
- 池中题目超过 7 天未更新 + 该考点仍为学生薄弱项 → 主动触发 AI 生成补充
- 池中题目 < 5 道 → 自动触发预生成，确保足够的变体量

**下一步**：将 3 个刷题功能的出题逻辑从"SQL 查库"改造为"AI 生成 + 缓存"，把 AI 真正推到出题引擎的位置。

## 十三、AI 生成题目的正确性验证（关键生命线）

> ⚠️ 这是决定 AI 出题能否真正上线的工程底线。LLM 可能产生题干与答案不匹配、题目无解/条件矛盾、计算过程正确但结果错误等幻觉。缺少验证环节会严重损害产品信任。

### 13.1 自动验证管线

```
AI 生成题目 + 解析
        │
        ▼
┌─────────────────────────────────────────┐
│  Step 1: 符号运算校验（数学计算题）        │
│  · LaTeX 规范化（Sanitizer）：正则清洗噪声  │
│    将 AI 输出标准化为 SymPy 可解析格式      │
│  · SymPy 重新求解，与 AI 答案比对         │
│  · 形式不同但数学等价？→ 随机点数值代入    │
│    （定义域内取3点，差值<10⁻⁶→等价通过）    │
│  · 不匹配 → 验证失败（见 Step 3）         │
│  · SymPy 无法求解（复杂题）→ 跳过，走 Step 2│
├─────────────────────────────────────────┤
│  Step 2: 合理性检查（所有题型必过）        │
│  · 选择题：正确选项是否唯一？             │
│  · 填空题：分母不为零？区间开闭正确？     │
│  · 改写题：数值范围/条件是否自洽？         │
│  · 不通过 → 验证失败（见 Step 3）         │
├─────────────────────────────────────────┤
│  Step 3: 验证结果分流                     │
│  · Step2 通过 → 存入 question 表         │
│  ·   SymPy 通过的标注"经符号运算验证"     │
│  ·   仅 Step2 通过的标注"经基础校验"      │
│  · Step2 失败 → 丢弃 + 日志 + 重试       │
│  · 连续失败 3 次 → 人工抽检队列          │
└─────────────────────────────────────────┘
```

### 13.2 验证覆盖范围

| 题型 | 验证方式 | 工具 |
|------|---------|------|
| 数学计算题 | 符号求解 + 数值代入 | SymPy / WolframAlpha |
| 选择题 | 选项唯一性 + 干扰项合理性 | 规则检查 |
| 填空题 | 答案值域合理性 | 规则检查 |
| 几何题 | 条件完备性 + 多解检验 | 规则检查 + LLM 自检 |
| 概率/应用题 | 答案值域 + 数值模拟验证 | 规则检查 + Monte Carlo 模拟 |
| 证明题 | 逻辑步骤自洽性 | LLM 自检（二次 Prompt 或模型投票） |
| 改写题 | 合理性检查（数值范围/条件自洽） | 规则检查（跳过符号求解，原题骨架已验证） |

> **实施提醒**：几何题、概率应用题、证明题的自动验证覆盖率有限。前期保持较高的人工抽检比例（建议 20-30%），积累信心后再逐步放宽。
>
> **验证标注区分**：通过 SymPy 的标注 `"AI 生成，经符号运算验证"`，仅通过合理性检查的标注 `"AI 生成，经基础校验"`。改写题（语义缓存产物）只过合理性检查。

### 13.3 验证失败的处理

- 单次失败 → 丢弃本题，同参数重试一次
- 连续 3 次失败 → 降级到题库 SQL 查询 + 告警日志
- 失败率监控 → 超过 5% 则暂停该考点/题型的 AI 生成，切回纯题库模式

### 13.4 用户反馈闭环

- 每道 AI 生成的题目解析末尾标注验证方式：
  - `"AI 生成，经符号运算自动验证"`（SymPy 校验通过）
  - `"AI 生成，经自动推理校验"`（LLM 自检通过）
- 附带 `[题目有误？]` 反馈入口
- 用户报错处理（区分题目来源）：
  - `source = 'official'`（公共题库）：≥2 名不同用户报错才下架（防单人恶意滥用）
  - `source = 'ai-generated'`（个性化生成）：单用户报错即对该用户下架（因该题仅此用户可见），后台异步人工/AI 复核
- 同一考点报错 > 3 次 → 暂停该考点 AI 生成，排查 Prompt 或模型问题

## 十四、已知限制与远期改进

> 以下为当前阶段明确不解决、但在生产环境需重新评估的设计决策。

### 14.1 符号验证覆盖度

SymPy 可覆盖约 60-70% 的考研数学计算题（求导、积分、方程求解），但复杂级数、抽象证明、含参讨论超出其能力。无法求解时系统走"合理性检查"降级，而非丢弃题目。WolframAlpha API 作为补充，但其按调用收费、单次延迟 3-10s，仅用于高价值场景（组卷中的解答题）。

### 14.2 外部 API 成本

当前未做全量成本测算。以下为 Phase 2 上线前必须评估的项目：

| 成本项 | 估算方式 | 备注 |
|--------|---------|------|
| LLM 题目生成 | ~500-1000 Token/题 × 日均新题数 | 缓存命中后归零 |
| Embedding 向量化 | 每份笔记 ~2000 Token | 一次性成本 |
| WolframAlpha | 按调用次数 | 仅用于解答题验证 |
| Mathpix OCR | 按页数 | 仅用于手写笔记上传 |
| Milvus 存储 | 每用户 Collection 资源开销 | 千级用户可接受 |

### 14.3 缓存 weekId 边界

缓存 Key `gen:{userId}:{kp}:pool:{weekId}` 中 weekId 为自然周。周日 23:59 请求后 1 分钟缓存失效，命中率瞬时下降。Phase 2 可改为滚动窗口（最近 7 天），避免边界效应。

### 14.4 AI 题目与真题的 UI 区分

`source` 字段枚举：`official`（人工录入真题）/ `ai-generated`（AI 生成）/ `user-contributed`（用户上传）。列表中混展时需前端强制区分标签，避免用户误认。

### 14.5 用户上传题目的质量控制

当前 `source = 'user-contributed'` 的题目直接入库，无审核流程。若标签错误会污染 SQL 匹配和自适应推荐。Phase 2 需增加：上传题目默认 `status = 'draft'`，管理员审核后改为 `published`，或走 AI 自动校验（考点标签是否匹配题目内容）。

### 14.6 降级体验一致性

验证连续失败降级到 SQL 题库时，当前种子数据的解析为通用模板，与 AI 生成解析风格不一致。Phase 2（AI 出题改造完成后）可考虑降级时对 SQL 题目套一层 AI 解析包装（解析走 LLM 生成，题目走题库），保持解析风格统一。
